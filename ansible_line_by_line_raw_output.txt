Original: 3 * How you will call an handler in a task ?
Answer: Handlers in Ansible are special tasks that only run when notified by another task using the `notify` keyword. They are typically used to restart services or trigger other actions that should only occur if a change has been made by a task. A task notifies a handler by its name (defined in the `handlers` section of a playbook). For example: `notify: Restart Nginx`.

Original: 4 * What is ansible registery ?
Answer: The term 'Ansible registry' likely refers to the `register` keyword in Ansible. The `register` keyword is used in tasks to capture the output of a command or module execution into a variable. This variable can then be used in subsequent tasks for conditional logic, logging, or extracting specific information. Example: `shell: cat /etc/hostname\n  register: hostname_output` will store the output of `cat /etc/hostname` in the `hostname_output` variable.

Original: 5 * How to use web command to run a loop in ansible ?
Answer: Ansible Ad-Hoc commands are simple, one-liner commands used for quick tasks without writing a full playbook. To run a loop-like operation with an ad-hoc command, you can use the `-e` flag to pass extra variables, often combined with the `with_items` equivalent or by directly using shell looping constructs if the module supports it. For example: `ansible <hosts> -m shell -a 'echo {{ item }}' -e "items=['item1','item2']"`. However, complex loops are better handled in playbooks.

Original: 9 * how playbook works in ansible.
Answer: An Ansible Playbook works by executing a series of tasks defined in YAML format against a specified set of hosts from your inventory. Ansible parses the playbook, connects to the target hosts (usually via SSH), and runs the tasks in order. Each task calls an Ansible module to achieve a desired state (e.g., install a package, start a service, copy a file). Playbooks can also include roles, handlers, and variables to create more complex and reusable automation.

Original: 12* write a palybook and explain it
Answer: To write a playbook, you create a YAML file. Here's a simple example to install and start nginx:
```yaml
---
- name: Install and start Nginx
  hosts: webservers
  become: yes
  tasks:
    - name: Install Nginx package
      ansible.builtin.apt: # or 'yum' for RedHat based
        name: nginx
        state: present
        update_cache: yes
    - name: Start Nginx service
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: yes
```
Explanation:
- `name`: Describes the play.
- `hosts`: Specifies target hosts from inventory.
- `become: yes`: Escalates privileges (like sudo).
- `tasks`: A list of actions.
  - First task installs nginx using the `apt` (or `yum`) module.
  - Second task ensures the nginx service is started and enabled using the `service` module.

Original: 14* what are the types of inventory in ansible
Answer: Ansible supports two main types of inventory:
1. **Static Inventory:** A plain text file (INI or YAML format) where hosts and groups are explicitly listed.
2. **Dynamic Inventory:** A script (e.g., Python, Bash) or a plugin that fetches inventory information from external sources like cloud providers (AWS, Azure, GCP), CMDB systems, or virtualization platforms. This allows inventory to be automatically updated as infrastructure changes.

Original: 15* Ansible: how do you call a playback inside another playbook: import it
Answer: You can call one Ansible Playbook from another using `import_playbook` or `include_playbook`. `import_playbook: other_playbook.yml` is static and processed at playbook parse time, making it generally preferred. `include_playbook: other_playbook.yml` is dynamic and processed during execution. These allow you to break down complex automation into smaller, manageable playbooks.

Original: 20* different between chef & Ansible
Answer: Key differences between Chef and Ansible:
1. **Agent vs. Agentless:** Chef is agent-based (Chef client on nodes), Ansible is agentless (uses SSH/WinRM).
2. **Language:** Chef uses Ruby DSL, Ansible uses YAML.
3. **Model:** Chef is primarily pull-based, Ansible is primarily push-based.
4. **Setup:** Ansible is generally simpler to set up.
5. **State Management:** Both manage state idempotently but approach it differently due to their architecture.

Original: 34* How do you copy output of one playbook as input to another playbook
Answer: To pass output from one playbook to another, you typically write the output to a file (e.g., JSON/YAML using `copy` module with `content`) or use fact caching (like Redis or JSON file backend). The second playbook can then read this file using `include_vars` or access cached facts. For more direct integration, consider structuring as roles or using tools like Ansible Tower/AWX workflows which can chain playbooks and pass artifacts.

Original: 35* How do you include 2, 4, 6 tasks of one playbook to another playbook
Answer: You don't directly include specific tasks from one *playbook* file into another by line number. Instead, you should extract those common tasks into a separate task file (e.g., `common_tasks.yml`). Then, in any playbook where you need those tasks, you can use `include_tasks: common_tasks.yml` (dynamic) or `import_tasks: common_tasks.yml` (static). This promotes reusability.

Original: 36* If i have 2 ansible roles, how will I copy output of one role to another role
Answer: To pass data (output) from one Ansible role to another within the same play, you can use `set_fact` in the first role to register a variable with the desired output. This fact then becomes available to subsequent roles in that play. For example, Role A: `set_fact: my_shared_data={{ some_task_output.stdout }}`. Role B can then use `my_shared_data`.

Original: 38* Explain how you set up Ansible
Answer: Setting up Ansible involves:
1. **Control Node:** Choose a Linux/Unix machine (or WSL on Windows).
2. **Install Ansible:** Use package managers (`apt`, `yum`) or `pip`.
3. **Inventory:** Create an inventory file (e.g., `/etc/ansible/hosts` or custom path) listing your managed nodes.
4. **SSH Access:** Ensure the control node has SSH access (preferably key-based) to managed nodes.
5. **Python on Managed Nodes:** Ensure Python is installed on managed nodes, as most modules require it.
6. **(Optional) `ansible.cfg`:** Configure default settings.

Original: 39* Which extension does those plugins have
Answer: Ansible plugins are typically Python files (`.py`). They are placed in specific directories named after the plugin type (e.g., `filter_plugins/`, `lookup_plugins/`, `callback_plugins/`) either adjacent to the playbook, inside a role's directory structure, or in configured global plugin paths. Custom modules are also often Python files but can be any executable that returns JSON.

Original: 43* how to copy the files from remote to local in ansible?
Answer: To copy files from a remote managed node to the local Ansible control machine, you use the `fetch` module. Example:
```yaml
- name: Fetch remote file
  ansible.builtin.fetch:
    src: /path/on/remote/file.txt
    dest: /path/on/local/fetched_files/
    flat: yes # Optional: to avoid host-named subdirectories
```
